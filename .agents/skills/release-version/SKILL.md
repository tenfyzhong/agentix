# Release version

Use this repository's committed-version release process. Invoking this skill to
release a version authorizes creating/pushing the release branch and PR, waiting
for CI, squash-merging that PR, creating/pushing its annotated tag, approving the
generated development PR workflow runs, and squash-merging that PR after
successful checks. Creating
or editing this skill is not itself a request to release anything.

## Required input

Require the user to supply exactly one stable `X.Y.Z` version (numeric components,
no leading zeros, no `v`, prerelease suffix, or build metadata). If missing or
ambiguous, ask for it before any release mutation. Never choose the next patch
or minor version for the user. Use the supplied value as `VERSION` below.

Read repository `AGENTS.md` and the Releases section of `CONTRIBUTING.md`.
Use the repository's Taskix tracking workflow when enabled.

## Repository scope and resume

Resolve `REPO` as the verified release repository's `OWNER/REPO` from its Git
remote before changing directories. Pass `-R "$REPO"` to every repository-scoped
`gh pr`, `gh run` or `gh release` command. For repository inspection, use
`gh repo view "$REPO"`. For `gh api`, use
explicit `repos/$REPO/...` endpoints; that command does not accept `-R`.
Do not rely on the current directory to select the repository.

On resume, inspect the existing release PR, annotated tag, Release runs and
development PR before making changes. Verify their repository, version and
commit identities, then continue from the first unfinished stage:

- Reuse a verified merged release PR and its squash SHA; do not recreate it.
- Reuse its matching annotated tag and successful Release run. Do not push the
  tag again or dispatch/rerun an already successful publication.
- For an in-progress run, keep watching it. Approve only runs currently requiring
  approval; do not repeat approval for queued, running or successful runs.
- If the development PR is already merged, verify its merge commit is on main
  and contains `$VERSION+dev`, then report completion without merging again.
  Check the version at that merge commit; a later main version must not be
  reset. The new-release version-order check and open-PR base-version check
  below apply only to their unfinished stages.

## Prepare the release PR

1. Locate the repository and the worktree holding `main`. Check its status and
   remote. Preserve unrelated changes; do not stash, reset or discard them.
   Update main with `git pull --ff-only origin main` from that clean worktree.
   Stop on divergence rather than forcing it. Record the updated base SHA.
2. Fetch tags and check both local and remote `refs/tags/$VERSION`. A conflicting
   existing tag is a blocker: never delete, move or force-push a release tag.
   Also require the requested numeric version to be newer than the stable part
   of main's VERSION and existing stable release tags. Compare numerically,
   not lexically. An existing release is handled only as a verified resume.
3. Create branch `release/$VERSION` from the updated main and its matching
   worktree at `<repository>/.git/wtm/release/$VERSION`; switch the working
   directory there. If that branch/worktree or a same-branch PR exists, inspect
   its base, commits, diff and state before resuming; do not reset or overwrite it.
4. Run:

   ```sh
   make prepare-release VERSION="$VERSION"
   make check-versions TAG="$VERSION"
   git diff --check
   ```

   Review the full diff. Only the version changes generated by prepare-release
   belong in this PR; do not include release tooling, source fixes or docs.
   If the targets are missing, stop and report that the release tooling must
   land first. Never reconstruct a different release process ad hoc.
5. Stage only those reviewed version files and create a signed-off commit with
   an English subject, `chore: release X.Y.Z`, using `git commit -s`. Inspect the
   resulting commit and diff before pushing the explicit release branch.
6. Create a PR to `main` with title `chore: release X.Y.Z`, explaining the version
   change and successful version checks. Write multiline text to a temporary
   file and use `gh pr create -R "$REPO" --body-file`; reuse the matching open PR on retries.
   Report its URL. Do not label arbitrary changes as a release to bypass tests.

## Wait and squash merge

1. Record the PR's exact `headRefOid`. Wait for its workflows/checks to finish
   (`gh pr checks PR -R "$REPO" --watch` and inspect workflow runs for that SHA). Missing
   checks, queued runs, cancelled runs or failures are not success. Wait for CI
   discovery rather than treating an empty check list as approval.
2. Both Tests and CI workflows must have a successful `Classify release PR` job proving
   the entire diff is exactly a prepared version change. Their test, formatting/Clippy,
   monitoring, and tmux jobs may then be skipped. All other applicable checks must
   succeed. Never bypass branch protection, required reviews or failed checks.
3. Re-read PR head and base before merging. If either changed since validation,
   update the release branch as needed and wait for the new head's checks again.
   Keep this PR version-only; fix unrelated failures separately.
4. Squash merge the checked head with:

   ```sh
   gh pr merge PR -R "$REPO" --squash --match-head-commit "$HEAD_SHA" --subject "chore: release $VERSION" --body-file "$MERGE_BODY_FILE"
   ```

   Prepare the English merge body with the release summary and a real
   `Signed-off-by: Name <email>` from the configured Git identity. Do not use
   `--admin` or bypass checks. If GitHub queues the merge, wait until the PR
   actually reports `MERGED`. Read and retain its `mergeCommit.oid`.

## Tag and publish

1. Fetch main and tags again; fast-forward the clean main worktree. Verify the
   recorded squash commit is on `origin/main`. Do not assume current main HEAD
   is that commit: another PR may already have merged.
2. Check out the recorded merge commit in the release worktree (after confirming
   it is clean) and rerun `make check-versions TAG="$VERSION"`. This verifies
   the exact commit to be tagged, not a newer main checkout.
3. Find the preceding stable tag and read its commit range through the squash
   commit. Draft an English annotated-tag message from those actual changes.
   Create the annotated tag at the explicit squash SHA using `git tag -a` and
   a message file. Verify its object type, peeled commit and message.
4. Push only `refs/tags/$VERSION` to origin. Verify the remote annotated tag and
   peeled commit using `git ls-remote --tags`. Never use `--tags` or force-push.
   On retry, reuse an existing tag only if it is annotated and points to this
   verified merge commit; a tag conflict requires user resolution.
5. Wait for the Release workflow for that tag/commit to complete successfully,
   including publication and `prepare-development`. Verify the published assets.
   A queued, running or failed release is not complete. Diagnose failures and
   rerun only affected jobs after resolving their cause; never retry indefinitely
   or move the tag. Continue with the development PR below.

## Complete the development PR

1. Find the same-repository `development/$VERSION` PR targeting `main`, created
   by the successful Release run. Record its number, head SHA and base SHA.
   If preparation skipped because main already advanced, verify and report that
   state; do not create or merge a stale development PR. Reuse an already merged
   PR only after verifying its resulting version and merge commit.
2. Fetch its head and current main. Require main's VERSION to equal `$VERSION`,
   the release tag to be an ancestor of main, and the PR to change it to
   `$VERSION+dev`. Prove the complete tree is a generated version-only change
   using `isReleaseOnly` from `scripts/release-pr.mjs` with the recorded base,
   head, branch, `event: "pull_request"` and verified same-repository identity.
   Do not approve workflows or merge based only on the branch name.
3. Discover the CI and Tests runs for this exact PR/head. A PR created with
   `GITHUB_TOKEN` can require workflow approval. Such a run can have
   `status: completed` with `conclusion: action_required`; this is waiting for
   approval, not a successful check. Using the authenticated maintainer's `gh`
   session, approve only the verified PR/head's runs with that conclusion:

   ```sh
   gh api --method POST "repos/$REPO/actions/runs/$RUN_ID/approve"
   ```

   After approval, re-query the runs and follow their current status and
   conclusion through to success. An approval response alone does not prove
   execution or success. Do not repeatedly approve while waiting for the state
   to update; re-read before considering any retry.

   This approves execution, not the PR review. If GitHub rejects approval,
   inspect the reason and report the blocker; do not weaken repository policies.
   The optional `RELEASE_PR_TOKEN` (GitHub App installation token or PAT with
   Contents and Pull requests write access) avoids this approval gate when
   creating the PR. Do not copy a local login token into repository secrets.
4. Wait for both CI and Tests on the exact head. Both `Classify release PR` jobs
   must succeed; their gated execution jobs may skip. All other applicable
   checks must succeed. Empty checks, pending approval, cancellations and failures
   are not success. Inspect failed jobs before deciding whether to fix or retry.
5. Re-read head and base immediately before merging. If either changed, repeat
   the version proof and check validation. If a newer release superseded this PR,
   stop instead of reverting its version. Squash merge using
   `gh pr merge PR -R "$REPO" --squash --match-head-commit "$HEAD_SHA"`, an English subject
   `chore: start X.Y.Z+dev development`, and a body file with the release context
   and a real Git-identity Signed-off-by line. Honor required reviews and branch
   protection; never use `--admin`.
6. Wait until GitHub reports `MERGED`, fetch main, and verify the recorded merge
   commit is on main and contains the expected development version. Report the
   release PR/tag, successful Release run, development PR/checks and squash SHA.
